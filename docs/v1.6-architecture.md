## Core rule

The LLM/LangGraph Agent never receives direct database, filesystem, shell, or arbitrary Java reflection access.

It can only call tools registered by `@AgentTool`.

## Tool lifecycle

1. Spring starts.
2. `ToolRegistry` scans Spring beans for `@AgentTool`.
3. It extracts tool name, description, permission, timeout and JSON-schema-like input metadata.
4. LangGraph calls `GET /internal/agent/tools` for discovery.
5. LangGraph invokes `POST /internal/agent/tools/{name}/execute`.
6. Java checks principal + permission.
7. Java validates arguments.
8. Java executes only the registered method.
9. Timeout is enforced by the executor.
10. Audit event is written to application logs.
11. Result is returned to LangGraph.

## Why this architecture matters

This makes Java the stable business/tool layer and Python/LangGraph the orchestration layer.

Later you can add:

- `@AgentTool(name="queryUser")`
- `@AgentTool(name="searchKnowledgeBase")`
- `@AgentTool(name="readExcel")`
- `@AgentTool(name="writeExcel")`
- `@AgentTool(name="createOrder")`
- `@AgentTool(name="sendNotification")`

without giving the LLM unrestricted infrastructure access.

## Production hardening for V1.7+

- Internal authentication: mTLS or service JWT.
- Permission service / RBAC instead of demo principal mapping.
- Redis-based rate limits.
- Postgres audit table.
- JSON Schema validation with a dedicated validator.
- Per-tool concurrency limits.
- Circuit breaker.
- Idempotency key for side-effecting tools.
- Tool risk levels: READ / WRITE / DESTRUCTIVE.
- Approval workflow for WRITE/DESTRUCTIVE tools.
- Do not rely only on `Future.cancel(true)` for hard cancellation; underlying DB/HTTP clients must have real timeouts.
